# Project Language — Design System Foundation

Версия: 0.1  
Статус: проектирование, не реализация

Этот документ описывает визуальную систему Project Language для MVP и последующего
расширения продукта. На текущем этапе документ не изменяет существующий интерфейс.

## 0. Текущая визуальная база

Перед проектированием системы были изучены:

- `PRODUCT.VISION.md` и `copilot-instructions.md`;
- `src/index.css`;
- `src/App.css`;
- `src/App.tsx`;
- `src/components/layout/Sidebar.tsx`;
- страницы и компоненты `src/features/vocabulary/`;
- страницы и компоненты `src/features/study/`.

Текущее состояние:

- приложение использует React, TypeScript и Vite без UI-библиотеки;
- основной маршрут и layout находятся в `App.tsx` и `AppShell`;
- навигация реализована в `Sidebar.tsx`;
- глобальные CSS-переменные находятся в `src/index.css`;
- большинство визуальных правил находится в одном `src/App.css`;
- текущие базовые цвета — светлая нейтральная поверхность, тёмный ink-текст и
  фиолетовый акцент;
- используются системный стек интерфейсных шрифтов и `Inter` как первый fallback;
- уже есть общие классы `.button`, `.search-field`, `.vocabulary-card`,
  `.study-flashcard`, `.study-rating-button`;
- есть адаптация для мобильного экрана примерно от `760px` и
  `prefers-reduced-motion` для Study Mode;
- отдельной темизации, отдельного слоя design tokens и общей библиотеки UI-компонентов
  пока нет.

Система ниже сохраняет сильные стороны текущего интерфейса — спокойный фон,
фиолетовый акцент, мягкие поверхности, компактную навигацию и крупную типографику —
но задаёт единые правила для дальнейшего роста.

## A. Design philosophy

### Визуальная идентичность

Project Language — спокойное рабочее пространство для самостоятельного изучения
языка. Визуальный характер: **modern minimal с элементами premium и живыми
акцентами в момент обучения**.

Интерфейс должен ощущаться:

- ясным, собранным и взрослым;
- достаточно выразительным, чтобы поддерживать мотивацию;
- спокойным при длительном ежедневном использовании;
- ориентированным на содержимое карточки и действие пользователя;
- универсальным для японского, китайского, корейского и других языков.

Premium-ощущение создаётся не декоративностью, а качеством типографики,
ритмом пространства, аккуратными границами, глубиной поверхностей и
предсказуемыми состояниями.

### Основные принципы

1. **Содержание важнее оболочки.** Слово, перевод, чтение и учебное действие
   должны быть визуально главнее декоративных элементов.
2. **Один экран — одна главная задача.** На странице должен быть один очевидный
   primary action.
3. **Прогрессивное раскрытие.** Расширенные сведения и настройки появляются по
   мере необходимости, а не занимают первый экран.
4. **Управление остаётся у пользователя.** Дизайн не должен навязывать темп,
   ежедневные лимиты или один способ обучения.
5. **Акцент используется экономно.** Фиолетовый направляет внимание, но не
   окрашивает весь интерфейс.
6. **Состояния должны быть понятны без цвета.** Ошибка, выбор, прогресс и
   disabled-состояние дополнительно обозначаются текстом, формой или контрастом.
7. **Языковая нейтральность.** Система не должна зависеть от длины английских
   строк или от одной письменности.
8. **Доступность по умолчанию.** Видимый focus, достаточный контраст, клавиатурное
   управление и reduced motion являются частью базового дизайна.
9. **Функциональность важнее полировки.** Visual changes should be made when
   they improve functionality, clarity, usability, or the learning experience.
   Visual polish alone is not a reason to delay functional product development.

### Приветствуется

- большие спокойные области пространства;
- короткие и ясные подписи;
- одна выразительная деталь на экране;
- карточки с понятной иерархией;
- живой акцент в Study Mode: оценка, прогресс, результат;
- аккуратная асимметрия, если она улучшает чтение;
- реальные состояния loading, empty, error и success.

### Следует избегать

- градиентов, не несущих смысловой функции;
- постоянных бейджей, всплывающих подсказок и декоративных иллюстраций;
- чрезмерно округлых игровых элементов;
- визуальной конкуренции нескольких primary-кнопок;
- плотных таблиц на мобильном экране;
- текста, который различается только цветом;
- анимации ради демонстрации анимации;
- копирования визуального языка Duolingo, Renshuu, Anki или SaaS-шаблонов.

### Простота при росте продукта

Каждая новая функция должна иметь:

- одну главную пользовательскую задачу;
- повторно используемые surface, typography и interaction tokens;
- минимальное число новых цветов и компонентов;
- понятное empty/error/loading-состояние;
- мобильное поведение, определённое до реализации.

Если новый компонент нельзя объяснить через существующий паттерн, сначала нужно
проверить, действительно ли он нужен, а не добавлять новый визуальный вариант.

## B. Color system

### Общие правила

Цветовые значения должны использоваться через semantic tokens, а не напрямую
в компонентах. Например, компонент использует `--color-bg-page`, а не
конкретный HEX. Это позволит переключать тему без переписывания компонентов.

В интерфейсе рекомендуется иметь один основной акцент — violet — и один
ограниченный учебный акцент — mint/teal для положительного результата. Красный,
янтарный и зелёный используются только для состояний.

### Контраст и применение

- Обычный текст должен соответствовать WCAG AA: ориентир не ниже 4.5:1.
- Крупный текст и графические элементы — ориентир не ниже 3:1.
- `--color-text-tertiary` предназначен только для второстепенной информации.
- Error, warning и success нельзя передавать только цветом: добавлять label,
  icon, status или понятный текст.
- Accent-soft не использовать для длинного основного текста.
- Destructive action не должен выглядеть как обычная secondary-кнопка.
- В Study Mode learning-цвет обозначает результат или завершение, но не
  заменяет оценку Again/Hard/Easy.

## C. Typography

### Шрифтовая стратегия

Новые зависимости и обязательная загрузка внешнего шрифта не требуются.
Рекомендуемый стек:

```css
font-family:
  Inter,
  ui-sans-serif,
  system-ui,
  -apple-system,
  BlinkMacSystemFont,
  "Segoe UI",
  sans-serif;
```

Для CJK-текста использовать отдельный fallback-стек:

```css
font-family:
  "Noto Sans JP",
  "Noto Sans CJK JP",
  "Hiragino Kaku Gothic ProN",
  "Yu Gothic",
  Meiryo,
  sans-serif;
```

Интерфейс не должен полагаться на наличие одного конкретного шрифта. Если
позже понадобится стабильная метрика, допустимо отдельно согласовать
self-hosted subset, но это не входит в текущий этап.

### Типографическая шкала

| Роль | Размер | Вес | Line-height | Использование |
|---|---:|---:|---:|---|
| Display | `44–56px` | 700 | `1.05` | Только ключевой заголовок страницы, не на каждом экране. |
| H1 | `32–46px` | 700 | `1.05–1.1` | Заголовок раздела. |
| H2 | `26–34px` | 650–700 | `1.1–1.2` | Заголовок карточки, empty state или summary. |
| H3 | `18–22px` | 650 | `1.25` | Подразделы и названия элементов. |
| Body large | `16px` | 400–500 | `1.55–1.65` | Важное описание и длинный explanatory text. |
| Body | `14px` | 400–500 | `1.5–1.6` | Основной интерфейсный текст. |
| Label | `12–13px` | 600–650 | `1.3–1.4` | Labels, buttons, поля. |
| Caption | `11px` | 500–650 | `1.35–1.45` | Metadata и вспомогательные подписи. |
| Eyebrow | `10–11px` | 700 | `1.4` | Короткая uppercase-категория с увеличенным tracking. |

Правила:

- Заголовки используют небольшой отрицательный tracking только при размере
  от `26px`; в обычном тексте tracking не уменьшать.
- Вес `650` допустим как промежуточный, если шрифт его поддерживает; при
  fallback использовать ближайший доступный weight.
- Длинные тексты ограничивать шириной около `60–70ch`.
- Placeholder всегда слабее основного label, но остаётся читаемым.
- Не использовать ALL CAPS для длинных фраз.

### Языковые символы

- Крупный термин на карточке Study: ориентир `48–72px` на desktop,
  `36–52px` на mobile; использовать `clamp()`.
- Размер должен уменьшаться при длинном слове, а не вызывать горизонтальный
  scroll.
- Межстрочный интервал для вертикально сложных CJK-строк — не ниже `1.25`.
- Японский термин, чтение и перевод должны быть визуально разными уровнями,
  но не тремя конкурирующими заголовками.
- Нельзя обрезать слово через `text-overflow: ellipsis`, если это скрывает
  учебный материал; использовать перенос или адаптивный размер.

## D. Spacing and geometry

### Шкала отступов

Базовая единица — `4px`. Рекомендуемые tokens:

| Токен | Значение | Применение |
|---|---:|---|
| `--space-1` | `4px` | Минимальный gap внутри метки. |
| `--space-2` | `8px` | Связанные label/value и компактные controls. |
| `--space-3` | `12px` | Внутренний padding небольшого control. |
| `--space-4` | `16px` | Стандартный gap и padding. |
| `--space-5` | `20px` | Разделение связанных блоков. |
| `--space-6` | `24px` | Padding карточки и разделение секций. |
| `--space-8` | `32px` | Основной внутренний отступ панели. |
| `--space-10` | `40px` | Разделение крупных областей. |
| `--space-12` | `48px` | Padding крупной пустой области. |
| `--space-16` | `64px` | Вертикальный ритм страницы. |
| `--space-20` | `80px` | Редкий hero/display spacing. |

Не добавлять произвольные значения без необходимости. Если нужен промежуточный
размер, сначала проверить, можно ли выразить его комбинацией существующих
tokens.

### Геометрия

| Token | Значение | Правило |
|---|---:|---|
| `--radius-sm` | `8px` | Малые labels, inputs и компактные элементы. |
| `--radius-md` | `12px` | Buttons, поля и небольшие карточки. |
| `--radius-lg` | `16px` | Основные карточки и панели. |
| `--radius-xl` | `22px` | Study card, summary и empty state. |
| `--radius-pill` | `999px` | Status, badges и progress track. |

- Основная граница — `1px solid var(--color-border)`.
- Не использовать одновременно толстую границу, сильную тень и яркий фон без
  явной иерархической причины.
- Базовая тень карточки: `0 18px 45px rgba(49, 39, 93, 0.06)` в Light theme;
  в Dark theme предпочтительнее слабая светлая граница и меньшая тень.
- Контентная ширина страницы: `max-width: 1060px`.
- Узкая задача, например Study session: `max-width: 760px`.
- Длинные формы: `max-width: 660–860px`.
- Основной content gutter: `40px` на desktop, `20px` на mobile.

### Сетки

- Использовать CSS Grid для повторяющихся списков и групп полей.
- Использовать Flexbox для toolbar, navigation и action row.
- Минимальный gap в списках — `8–12px`.
- Сетка не должна заставлять карточку становиться уже примерно `280px`;
  ниже этого порога элементы переходят в одну колонку.
- В Study главный объект всегда центрирован и не должен конкурировать с
  боковой панелью.

## E. Components

### Buttons

В продукте достаточно трёх визуальных уровней:

1. **Primary** — одно главное действие: accent background, `--color-on-accent`.
2. **Secondary** — безопасное дополнительное действие: surface background,
   border и secondary text.
3. **Text** — низкоприоритетное действие без контейнера, только для коротких
   переходов и вторичных команд.

Состояния:

- default — стабильный контраст и очевидная зона нажатия;
- hover — немного более сильный фон/граница, без резкого скачка размера;
- active — лёгкое смещение максимум `1px` или усиление фона;
- focus — видимый `2–3px` focus ring через accent;
- disabled — сниженный контраст и отсутствие cursor/hover; не скрывать причину
  disabled, если она неочевидна.

Минимальная высота обычной кнопки — `40px`, touch-target — не менее `44px`
на мобильных устройствах.

### Cards

Карточка имеет одну из ролей:

- content card — слово и его данные;
- action card — выбор режима или next step;
- learning card — Study flashcard;
- status card — empty, error, success или summary.

Карточка не должна одновременно быть и контейнером, и декоративным фоном для
нескольких независимых задач. Использовать единые border, radius и padding,
меняя только иерархию и состояние.

### Inputs

- Label всегда видим и связан с полем.
- Placeholder не заменяет label.
- Focus определяется border + focus ring, а не только сменой цвета.
- Ошибка отображается рядом с полем и связывается через `aria-describedby`.
- Search field сохраняет компактность, но не уменьшается ниже touch-friendly
  высоты.
- Textarea для японских примеров допускает перенос и не обрезает материал.

### Navigation

Desktop sidebar остаётся спокойной, с одной active-поверхностью и коротким
описанием раздела. Mobile navigation становится горизонтально прокручиваемым
рядом или компактным меню, но сохраняет те же labels и порядок.

Активный маршрут обозначается минимум двумя признаками: цветом и surface/формой.
Навигация не должна использовать яркий badge для каждого раздела.

### Progress indicators

- Progress bar показывает конкретное измеримое продвижение и всегда имеет
  текстовый контекст или доступное имя.
- Track — neutral border/subtle background, fill — accent или learning color
  в зависимости от смысла.
- Анимация fill короткая и не должна блокировать следующее действие.
- Для неопределённой загрузки использовать skeleton/spinner только при реальной
  работе, а не как декоративный эффект.

### Badges

Badge предназначен для короткого статуса: язык, уровень, JLPT, состояние.
Один badge — одна смысловая единица. Не использовать badge как кнопку без
явного интерактивного поведения.

### Modals / dialogs

- Нужны только для подтверждения destructive-действия, потери прогресса или
  важного выбора.
- Dialog имеет понятный заголовок, объяснение последствий и явные действия.
- Primary action — безопасное продолжение; destructive action визуально
  отличается и называется конкретно.
- При открытии focus переходит внутрь, Escape закрывает только безопасный dialog,
  background не должен оставаться интерактивным.
- Для простых inline-состояний modal не использовать.

### Empty states

Empty state объясняет, что произошло, почему это важно и какой следующий шаг.
Он должен содержать один primary action. Иллюстрация или mark — вторичны.

### Loading states

Loading должен соответствовать реальной длительности:

- короткое действие — disabled button с изменённым label;
- загрузка списка — компактный status или skeleton структуры;
- длительный процесс — progress, текущий статус и возможность отмены, если это
  безопасно.

Не показывать бесконечный spinner без объяснения и не маскировать ошибку
success-состоянием.

## F. Motion and animation

### Durations and easing

| Token | Значение | Применение |
|---|---:|---|
| `--motion-fast` | `120ms` | Hover, color и border feedback. |
| `--motion-standard` | `180ms` | Button state, progress и появление небольшого блока. |
| `--motion-slow` | `280ms` | Panel/dialog и смена крупного контента. |
| `--ease-standard` | `cubic-bezier(0.2, 0.8, 0.2, 1)` | Большинство переходов. |
| `--ease-emphasized` | `cubic-bezier(0.22, 1, 0.36, 1)` | Study card и появление результата. |

Принципы:

- Анимация объясняет изменение состояния, а не украшает неподвижный экран.
- Переход страницы должен быть коротким и ненавязчивым; не анимировать весь
  layout при каждом клике.
- Новые элементы могут появляться через opacity и небольшой translate
  `4–8px`.
- Progress animates from previous value to new value, но не должен замедлять
  чтение числового значения.
- Button feedback ограничивается цветом, border и лёгким `translateY(1px)`.

### Study Mode

- Reveal может использовать лёгкий opacity/transform transition в пределах
  `180–280ms`.
- Flip-анимация допустима только если она сохраняет читаемость, не вызывает
  motion sickness и не скрывает фактическое состояние от screen reader.
- Реальное состояние reveal хранится в React; CSS animation не определяет
  доступность ответа.
- После assessment следующая карточка появляется с коротким transition и
  логичным focus move.

### Когда анимация не нужна

Не анимировать:

- системные ошибки и критичные сообщения, которые должны быть замечены сразу;
- каждую строку длинного списка;
- простой переход focus;
- disabled state;
- контент, который пользователь должен прочитать немедленно;
- крупные изменения layout на слабых мобильных устройствах.

### Reduced motion

При `prefers-reduced-motion: reduce`:

- отключить transform/flip и длинные transitions;
- оставить мгновенную смену состояния и достаточный focus;
- не удалять информацию и не менять порядок действий;
- не использовать blinking или бесконечную декоративную анимацию.

## G. Responsive design

### Desktop

- Sidebar — фиксированная спокойная колонка примерно `240–280px`.
- Контент центрируется в пределах `1060px`.
- Toolbar и form groups могут использовать две колонки.
- Study card получает максимум свободного пространства и сохраняет
  центрирование.

### Tablet

- Sidebar может стать более компактной, но labels основных разделов сохраняются.
- Две колонки используются только если оба блока остаются читаемыми.
- Content gutter уменьшается до `24–32px`.
- Длинные selection lists получают собственный scroll, но не ломают страницу.

### Mobile

- Navigation становится горизонтальным рядом или compact navigation.
- Content gutter — около `20px`, vertical spacing уменьшается, но не исчезает.
- Toolbar, form actions и summary actions переходят в одну колонку при
  нехватке ширины.
- Touch target — не менее `44px`.
- Не использовать hover как единственный способ получить информацию.
- Большие японские символы используют `clamp()` и не вызывают horizontal scroll.

### Study Mode

- На desktop card-centered layout ограничен примерно `760px`.
- На mobile карточка занимает почти всю доступную ширину, но сохраняет
  внутренний padding `24–28px`.
- Assessment buttons располагаются вертикально или в устойчивой трёхколоночной
  сетке только если labels не становятся слишком узкими.
- Progress, position и action должны быть видны без прокрутки перед карточкой.
- Answer sections складываются в одну колонку; примеры получают достаточный
  line-height и не превращаются в плотную таблицу.

## H. Design consistency

При добавлении функции необходимо проверить:

1. Использует ли она существующие semantic colors, spacing, radius и motion
   tokens.
2. Есть ли один primary action и понятная иерархия.
3. Что произойдёт при empty, loading, error, success и disabled-состояниях.
4. Как компонент выглядит на ширине от `320px`.
5. Работает ли он с клавиатурой, focus-visible и screen reader.
6. Не передаётся ли смысл только через цвет.
7. Не дублирует ли новый компонент существующий `.button`, card, input или
   status pattern.
8. Не добавляет ли функция новый цвет без продуктовой необходимости.

Именование должно описывать роль, а не страницу. Предпочтительны
`surface`, `button-primary`, `status-error`, `study-card`, а не
`purple-box` или `library-purple-panel`.

Компоненты могут иметь feature-specific layout, но их базовые интерактивные
состояния, typography и tokens должны быть общими. Японские данные являются
содержимым, а не отдельной декоративной темой.

## I. Implementation roadmap

### 1. Создание CSS design tokens

- Перенести текущие цвета из `src/index.css` в semantic tokens.
- Добавить шкалу spacing, radius, shadow и motion.
- Сохранить обратную совместимость с существующими именами на переходный
  период или обновить call sites одной согласованной серией изменений.
- Подготовить `[data-theme="light"]` и `[data-theme="dark"]`; переключатель темы
  не реализовывать без отдельного UX-решения.

### 2. Обновление базовой типографики и глобальных стилей

- Зафиксировать interface и CJK font stacks.
- Уточнить base line-height, color, background, focus-visible и selection.
- Проверить контраст и отображение японских терминов на реальных карточках.
- Добавить reduced-motion правило на глобальном уровне.

### 3. Унификация общих компонентов

- Выделить минимальные повторяемые primitives: Button, Card, Field,
  Badge, Progress, EmptyState и StatusMessage.
- Не создавать компонент ради каждого существующего CSS-селектора.
- Сначала перевести Sidebar, vocabulary form/list и общие actions.

### 4. Редизайн Study Mode

- Применить tokens к setup, selection list, flashcard, assessment и summary.
- Сохранить существующую in-memory session logic и keyboard accessibility.
- Отдельно проверить крупные CJK-символы, reveal animation, focus и reduced motion.
- Не смешивать редизайн с изменением алгоритма обучения или permanent analytics.

### 5. Применение к Library, Add Words, Dashboard и Progress

- Перевести страницы по одной, начиная с Library и Add Words как центрального
  пользовательского потока.
- Затем обновить Dashboard и Progress, когда их функциональное содержание
  будет определено.
- После каждого этапа проверять desktop, tablet, mobile, empty/error/loading
  и сохранение существующего поведения.

## Решения, требующие отдельного согласования

1. Нужно ли включать ручной переключатель Light/Dark в ближайший MVP или пока
   подготовить только токены.
2. Оставлять ли `Inter` первым fallback без self-hosting либо позднее добавить
   контролируемый набор шрифтов.
3. Должен ли learning teal использоваться только в Study Mode или также в
   Progress и success-сообщениях.
4. Нужно ли вводить отдельные React UI primitives сейчас либо сначала провести
   token migration внутри существующих компонентов.
5. Нужно ли добавить compact mobile navigation вместо текущего горизонтального
   списка при расширении числа разделов.
